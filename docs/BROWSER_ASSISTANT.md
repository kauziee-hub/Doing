Multi-select planning produces a complete desired answer set; the host applies only differences and reuses that set while the question is unchanged. Next waits for the observed counter to change, so delayed navigation cannot trigger a duplicate click. A stale command proven not to have executed gets a fresh observation and plan, up to four consecutive retries. Unknown outcomes stop without replay. Going Next does not authorize final assessment submission; say submit explicitly when wanted. Reload the companion after upgrading.

0.5.3 / companion 0.7.1 adds whole-page explanations. “Go through this page and tell me what it is about” enters a host-owned read-only scan: scroll to the start, read visible sections, scroll down and maintain a bounded rolling answer. This path never calls the action planner and cannot click, type or submit. It stops after 50 read sections if a page keeps growing. Page/nested scrolling and explicit submission workflows remain available for action requests. Difficult coding and explicit careful-thinking requests on the GPU receive a longer reasoning/output budget; the companion waits up to 210 seconds for a step. App control does not grant browser access.

Doing's Chrome/Edge companion opens a chat in the browser side panel. Ask about an allowed page or describe what to do in ordinary language. Questions get a reply; action requests start a browser task, then report the result in the same conversation. Follow-up messages can refer to earlier messages. Everything uses the existing local Ollama model. The desktop **Browser assistant** section only handles connection setup and status.

## Setup and use

1. Keep Doing open. In **Browser assistant**, choose **Open extension folder**. Load that folder once using **Load unpacked** in `chrome://extensions` (or `edge://extensions`) with Developer mode enabled.
2. For an existing installation, reload the companion once after updating. The old popup offers **Reload companion update**. If needed, use Chrome's extension Reload button and approve its new permissions. The icon then opens a side panel.
3. Open a website, open the Doing side panel and click **Allow this tab**. Chrome may ask for this site's access. Approve the first browser connection in Doing with **Allow connection & remember**. No pairing code is entered.
4. Chat beside the page: “Which option is correct, and why?”, “Fill those answers but do not submit yet”, or “Solve this coding problem and type the complete solution into the editor.”
5. To submit or advance, say so: “Answer all ten questions, submit each and go next until results.” Without that instruction, advancing waits for a chat reply such as “yes, submit”. “Submit all remaining pages” grants continued submission for that task. There are no submission/task checkboxes.
6. After the task finishes, Doing replies in chat. Send another instruction or ask a follow-up. **Stop** cancels the current request while keeping tab access; **Revoke tabs** or Ctrl+Shift+Y revokes access. Ctrl+Shift+X in Doing stops the current task. A dispatched action may finish.

## Groups of tabs

Add up to eight tabs by selecting each website and choosing **Allow this tab** in the side panel. Each tab requires its own explicit addition. Tab chips select the default working page. Questions can use bounded text from the group, and a task can switch to another explicitly allowed tab, inspect its controls, and act there. **Group these tabs in Chrome** creates an actual Chrome tab group from the allowed tabs. Opening a new tab or adding an unrelated tab to that Chrome group does not grant Doing access.

The site boundary is checked for every allowed tab. Closing a tab, navigating it to another site, or using its × chip revokes that tab only and stops the current task. Other allowed tabs remain available. Removing the final tab revokes the group. Tasks do not create new tabs or automatically authorize other sites.

## Permissions and data

The local bridge starts with Doing on `127.0.0.1:19389`, before any page access. First connection uses a 192-bit secret generated by the companion and a desktop approval with a two-minute deadline. The approved secret/extension ID are encrypted with Windows DPAPI in `%APPDATA%/Hirora/browser-connection.bin`. The companion stores its secret locally in trusted extension contexts, never in sync. Authenticated requests require the exact loopback Host, bearer token, approved extension Origin and bounded validated JSON. Website origins are rejected.

The side panel uses Chrome's sidePanel API. Its Allow button requests optional host access only for the selected site's origin, then explicitly registers that tab in Doing's in-memory allowlist. Chrome host grants may remain in extension settings; Doing still requires a fresh per-tab Allow after browser/worker restart. The tabs permission supplies tab metadata for the selected page; it does not automatically add tab content to the model. tabGroups is used only for the user-invoked grouping button. The debugger permission supports browser input, attaches only during typing in an allowed tab, and shows Chrome's normal notice. No raw debugging port is opened.

Allowing a tab starts observations: up to 18,000 characters of visible DOM text, 180 controls with values/options/check states, and rendered editor text. Group context includes up to 2,500 characters from each tab. Model input is further bounded to fit the local engine. Observations, conversation and progress stay in memory and go to the local model only. They are not intentionally persisted. **New chat** clears the conversation and stops work. **Forget browser & revoke access** closes the bridge and removes remembered trust; browser site grants can separately be removed in Chrome's extension settings.

The chat model decides whether the latest message requests an answer, an action task or approval of a pending action. Read-only answers cannot dispatch commands. Both chat and action prompts treat page content as untrusted data. Submission requires the model's interpretation plus a conservative check of the latest user's message; earlier tasks and page text cannot grant it. Ambiguous or negated requests can require a follow-up. An instruction to submit every page can send answers or application details to that website.

Actions must target a currently observed control ID or an allowed tab ID. No model scripts, selectors or arbitrary URLs execute. Each command checks the page revision and task permission again immediately before dispatch. Unacknowledged commands never replay. Completion is based on the observed page; the progress count is actions, not questions or a score. Answers are discarded when the observed context changes during generation or access is revoked. Tasks have a 30-minute lease and 150-action UI limit (IPC maximum 300), and stop on lost connection, stale state, repeated no-progress actions or an error. Remembered connection trust never restores tab/task access after restart.

## Limits

- Common inputs, selects, native/ARIA options and top-level Monaco/CodeMirror/Ace editors are supported. Hosted editor compatibility varies.
- DOM text is not the whole screen: canvas content, closed shadow roots, cross-origin frames, hidden content, very long pages, file uploads, login and CAPTCHA can need manual help. Screenshot answers remain separate.
- Code entry verifies the requested code against rendered editor text; long virtualized code can stop for review.
- Personal application facts must be supplied in the conversation. The browser model does not automatically receive the knowledge database.
- The local 4B/1.7B model can choose wrong answers or actions. Review important information. Use assistance where permitted.
- Distribution is an unpacked extension, not a store listing. Doing 0.4.1 includes side-panel chat; 0.4.0 and older published installers lack this flow.
